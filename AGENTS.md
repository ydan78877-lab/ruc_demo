# Mobile Prototype Agent Guide

## Prototype Instructions

### Durable prototype decisions

#### Current WeChat CloudBase pilot (2026-08-22)

- The active production pilot is the Taro mini-program in `miniprogram/`, using WeChat login and the existing CloudBase environment `cloudbase-d1gtlpks0104b2e4f`. This supersedes the older Sign in with ChatGPT + Sites D1 account plan for the WeChat pilot.
- A first WeChat visit creates an account keyed by the server-observed WeChat OpenID. The required onboarding fields are real name, cohort (`19级` through `26级`), and major (`金融`, `国管`, `人管`, `法语`, `传播`, `数学`, `大数据`, `人工智能`, or `其他`). New accounts start with blank personal data; never seed the `林知夏` demo profile or demo experiences into a real account.
- Cloud persistence covers personal data plus the collaboration layer. Class/course spaces, memberships, join requests, owner/admin/member roles, shared matters, each member's own completion/confirmation state, personal matters/reminders, and course-resource metadata/version history follow the WeChat account and are authorized in the cloud function. Shared matters remain writable only by space owners and administrators; every student may create, edit, complete, restore, and delete personal matters that are visible only to that account. Course owners and administrators upload supported files of at most 20 MB to CloudBase object storage; every current or historical space member may download the versions exposed by the authorized resource-download action. The read-only case library continues to be maintained through the existing Feishu sync workflow.
- Personal data follows the WeChat account across devices. Explicit save commits to CloudBase; local storage is only an in-progress draft/cache. Account disabling retains all data and blocks use; restoring the account restores access. The first version does not permanently delete accounts.
- The management surface is a separate HTTPS web admin. One super-administrator can view and edit every user and personal-data field, disable or restore accounts, bind one account as the local developer account, review audit logs, and export user/profile/experience data to Excel. Case-library editing is out of this admin's first-version scope.
- The local H5 demo must use the administrator-bound real developer account and the same CloudBase data as that account's mini-program session. UI and business logic remain shared with the mini-program; local H5 writes are real writes and must never rely on an exposed OpenID or embed administrator credentials in client code.
- The desktop H5 demo is a review surface for the current mini-program, not the legacy browser prototype. Keep it centered in a 430px phone canvas and bind Taro's desktop root-rem scale to that canvas so rpx-derived typography and spacing match the mini-program instead of scaling from the full browser width. Keep this preview scaling H5-only; never change the native WeChat rpx or real-device navigation layout to fix desktop presentation.
- Preserve the current mini-program page structure and visual design. Add only the account/bootstrap/onboarding flow, blank/loading/error/disabled states, cloud-save feedback, and the data adapters required for real accounts.
- The real mini-program must remain usable on both iPhone and Android devices. Every custom navigation surface reads its top inset from WeChat's `getWindowInfo()`/menu-button metrics; never depend on iOS-only CSS safe-area values or a browser-only status-bar variable for native positioning. Keep app-owned controls below the device status bar and to the left of WeChat's native capsule.
- Collaborative maintenance uses the private GitHub repository `lhxy2023-alt/ruc-suzhou-student-app`. `develop` is the shared integration branch and must use a separate CloudBase development environment containing synthetic data only; `main` represents the internal-test production environment. The technical collaborator may modify the mini-program, cloud functions, and web admin but must not receive production-database, real-user-data, super-administrator, or release credentials. Feature branches merge into `develop` by pull request; releases merge `develop` into `main`, and only the owner uploads WeChat experience or production versions.
- The current information architecture no longer exposes a `模版` concept. The home page has four independently collapsible sections in this order: `我的待办`, `我的班级`, `我的简历`, and `我的目标`. `我的简历` is an account-owned surface outside every goal and includes `教育背景`, `实习经历`, `科研与竞赛`, `校园经历`, `语言与标化`, `兴趣与技能`, and `其他`; a goal may read account data for progress but must never own or display a resume copy.
- Goals use at most three menu levels: goal, sub-goal, and category; concrete checklist entries sit below the category and are not a fourth menu. `毕业目标` is a protected first-level account goal, not a child of an admissions goal. On onboarding it is generated from cohort plus major for matched 25/26 training-plan rule packs, while unmatched cohorts/majors receive the Finance demo as a clearly labelled reference. The generated goal is an editable personal copy with source/version provenance and a reset action. `25中法保研` is a separate first-level goal whose current child is `推免资格获取`. User-created goals such as `港新申请` support user-created sub-goals, categories, content, requirements, and descriptions; their leaf completion is always a manual checkbox and never an inferred admissions score.

## Runtime Contract

- Preserve the mobile device runtime unless the user's task explicitly asks otherwise. Do not replace it with a standalone page. Visual fidelity applies to app-owned content inside the device screen, not to template-owned device chrome.
- Keep `App` composed around `PhoneFrame` -> `KeyboardProvider`, with `StatusBar`, app content, and `HomeIndicator` mounted inside the phone frame. For this demo, pass `enabled={false}` to `KeyboardProvider` and do not mount `KeyboardDock`, so the simulated keyboard never appears or changes viewport insets. `StatusBar` and the iOS home indicator are overlaid device chrome. When the Android keyboard is closed, the app viewport reserves the protected navigation-bar region instead of painting behind it. iOS screens continue to paint behind the home-indicator area and own their safe-area content padding.
- Preserve the `iPhone` / `Pixel 10` device picker and both calibrated device presets. The Pixel screen is `427 x 952`; its `32 x 32` camera circle and `web/public/assets/android/navigation-bar.svg` bottom navigation bar are protected device chrome, not app content.
- Preserve the device picker's intentionally lightweight Codex styling in the top-right corner: its trigger wrapper is borderless and transparent, its trigger sizes to content, and its right-aligned menu uses the compact 3px inset plus the specified hairline and elevation shadow layers. Keep the prototype root and default app screen white.
- Preserve `StatusBar` as live device chrome, including its platform-specific typography, source status-icon assets, and spacing. Pixel 10 uses Roboto, Android indicators, and 32px top, left, and right padding. iPhone uses its iOS indicators, system typography, and calibrated spacing. Do not hardcode screenshot times like `9:41` into the status bar, replace its real-time clock, or move status bar content into app markup unless the user explicitly asks for a fixed/mock device time.
- `PhoneFrame` owns the calibrated device frame, screen portal, device picker, camera cutout, and custom cursor. Keep device assets in `web/public/assets/iphone/` and `web/public/assets/android/`; if an asset fails to load, repair the asset path or restore the asset instead of removing the frame, keyboard, or image render.
- Use `MobileScroll` directly for simple single-screen prototypes. Use `FlowStack` for conventional multi-screen flows whose routes can own their fixed header and footer; when using it, define each route as a `FlowScreen`: `{ id, header?, headerHeight?, footer?, footerHeight?, render }`, and use `flow.push(screen)`, `flow.pop()`, and `flow.replace(screen)` from `FlowStack` render callbacks or `useFlow()` instead of introducing another router.
- Use `Carousel` for a carousel, horizontal rail, swipeable cards, image or media strip, horizontally scrollable cards, chip rail, or other horizontal collection.
- For a layered app shell—such as a persistent composer, independently presented sheet, pushed/peek sidebar, or app-wide transition—compose directly in `Prototype.tsx` rather than forcing it through `FlowStack`. Keep app-owned fixed chrome as sibling layers outside `MobileScroll`.
- When using `FlowScreen`, put route-owned fixed headers or footers in `FlowScreen.header` or `FlowScreen.footer`. Set `headerHeight` to the visible app-toolbar height; `FlowStack` adds the device's top safe-area/status-bar inset automatically. Do not include `StatusBar` or its height in the header. Set `footerHeight` to the full app-footer height. `FlowScreen.footer` is an overlay, not reserved layout space; screens using it must add their own bottom content padding such as `padding-bottom: calc(var(--flow-footer-height) + var(--mobile-safe-area-height) + 24px)` so final content can scroll above the footer while still painting behind it.
- Render only scrollable content inside `MobileScroll`; it is for content that should move with scroll and rubber-band overscroll. Keep app-owned headers, nav bars, tabs, composers, and overlays outside it. This keeps scroll physics, safe areas, keyboard insets, scrollbars, and drag click suppression active without letting content paint under fixed chrome.
- Buttons, links, cards, and images inside `MobileScroll` should still allow drag scrolling when the pointer moves beyond tap slop. Use `data-scroll-drag="ignore"` only for rare controls that must own the drag gesture themselves.
- Do not add `var(--keyboard-height)` to ordinary screen/content padding inside `MobileScroll`; the scroll viewport already shrinks above the simulated keyboard. For custom fixed composers, search bars, or toast chrome, use `useKeyboardInsets().bottomInset`. It is relative to the app viewport: Android returns `0` while the closed-keyboard viewport already reserves navigation, then returns the keyboard height while open; iOS continues to clear the home indicator while closed and ride directly above the keyboard while open. Do not pin custom bottom chrome to `bottom: 0` or only `keyboardHeight`.
- Use `KeyboardInput`, `KeyboardTextarea`, or `MobileTextField` for every text-entry control. A raw `input` or `textarea` disconnects focus, keyboard animation, safe-area insets, and attached surfaces.
- Use `BottomSheet` for phone-scoped sheets. Its props are `open`, `onOpenChange`, `title`, optional `description`, optional `snap`, and `children`; it renders through the phone screen portal and dismisses the keyboard before opening.

## Horizontal Carousels

- Use `Carousel` for horizontally draggable cards, images, media, chips, or other horizontal collections. Do not recreate these with `overflow-x`, custom pointer handlers, or a generic div.
- `Carousel` can be nested directly inside `MobileScroll`. It owns horizontal gestures and automatically yields vertical gestures to the parent.
- Never put `data-scroll-drag="ignore"` on or around a `Carousel`; doing so prevents vertical parent scrolling when a gesture begins inside it.
- Do not add CSS scroll snapping to `Carousel`; its runtime owns momentum and release motion.
- Use `data-scroll-drag="ignore"` only when a control must prevent parent scrolling in every drag direction.

See `web/src/mobile/COMPONENTS.md` for the full component and gesture contract.

## Keyboard Rule

The simulated keyboard is a separate top-layer component. Before presenting anything that behaves like iOS navigation or modal UI, dismiss it first.

Call `keyboard.hide()` before:

- pushing, popping, or replacing FlowStack routes
- opening bottom sheets, action sheets, dialogs, menus, or navigation sheets
- starting transitions where the destination should not inherit text-input focus

`FlowStack` already hides the keyboard for `push`, `pop`, and `replace`. `BottomSheet` already hides it before opening. If you add new modal/sheet/navigation primitives, follow the same rule.

When a composer, search surface, or other keyboard-attached component closes, call `keyboard.hide()` in the same event before changing that component's open state. Position attached surfaces from `useKeyboardInsets()` rather than a separate timer or visibility flag so both dismiss together.

When any text-entry control loses focus, dismiss the simulated keyboard. If the control is custom or does not use the runtime's keyboard-aware fields, handle its blur event and call `keyboard.hide()` explicitly. Keep the keyboard open only when focus is moving directly to another text-entry control that should share the same keyboard session.

## Interaction Rules

- Do not trigger buttons or inputs after a pointer has become a drag. Preserve the drag suppression behavior in `MobileScroll`.
- Do not allow native browser image/file dragging inside the phone frame. Preserve the phone-level `dragstart` suppression and non-draggable image styles so scroll drags that begin on images still scroll the prototype.
- Use `KeyboardInput`, `KeyboardTextarea`, or `MobileTextField` for text entry so the simulated keyboard and safe-area insets stay connected.
- Fixed phone chrome should not animate with pushed screens. Screen content can animate; the status bar, camera cutout, and preview chrome should stay put.
- Keep the keyboard below the home indicator/safe area layer in z-index, and above ordinary app UI while visible.
- Keep the home indicator as the topmost safe-area layer in the z-index above everything else in the prototype.

## Campus Workspace Decisions

- Launch into `概览`; keep goal templates as secondary pages reached from the single primary-template card.
- `案例库` is a native full-page capability reached only from `功能中心` → `全部功能`. Preserve the source library's cases, interviews, search, filters, case details, real school logos, and contact QR assets inside the app design system. It is read-only for app users: never expose case creation, editing, upload, or publishing controls in the student app. The owner maintains content in the Feishu backend and explicitly syncs reviewed updates into the app. Do not use a WebView, add a separate home entry, or claim profile matching until that capability is explicitly designed.
- Show only campus items from class/course spaces in the overview agenda. Do not mix goal-template tasks into this timeline.
- The overview agenda and full matters page combine shared class/course matters with the signed-in student's private matters. Personal matters use the source label `个人事项`, never belong to a space, and remain private to the owning WeChat account. Creating, editing, completing/restoring, and deleting a personal matter must not require a class/course role.
- Keep `CampusDemoState` and its storage key independent from `StudentProfile` and `TemplateConfig`; resetting demo data resets all three domains without merging them.
- Use full pages for 事项、班级与课程、空间详情、事项详情/编辑和资料预览. Reserve sheets for lightweight filters, account, data-entry, and template-editing interactions.
- Full-page workspace navigation uses one consistent directional transition: forward navigation, including the overview grid launcher, slides the destination in from the right; back navigation enters from the left. Keep the motion short and subtle, preserve fixed device chrome, and honor `prefers-reduced-motion`.
- Campus spaces use three roles modeled after group chats: exactly one `空间负责人`, at most three `管理员`, and ordinary `成员`. The creator becomes the space owner. Owners and administrators can publish, edit, and cancel matters, manage course resources, process join requests, and remove ordinary members. Only the owner can appoint or remove administrators, transfer ownership, reset the join code, change the join-review policy, and dissolve the space.
- Every member can see and copy the join code. The owner alone sees the `需要审核` switch and reset action; the switch is green and on for approval-required joining, gray and off for direct joining. Changing the rule only affects future join attempts and does not auto-resolve pending requests.
- Ownership may be transferred to any existing member. The previous owner becomes an ordinary member immediately and cannot leave before transferring or dissolving the space. Dissolving requires confirmation, invalidates the join code, blocks all further content and member writes, and moves the complete space history into the read-only `已解散空间` view; dissolved spaces cannot be restored or deleted in the demo.
- Course assets use the real WeChat message-file picker and CloudBase object storage. Owners and administrators may upload `pdf/doc/docx/ppt/pptx/xls/xlsx/txt/zip/jpg/jpeg/png/webp` files of at most 20 MB, replace a same-named resource as a new version, or keep it as a separate resource. Members may switch versions, download/open files, and save a version into WeChat's local mini-program storage for offline use. Never expose cloud file IDs in the shared snapshot; the authorized download action returns the selected version only after checking current or dissolved-space membership.
